# 抖音旧收藏队列快照恢复与冷却隔离设计

## 背景与根因

生产日志显示，抖音单作品详情接口连续两次返回 HTTP 200、`Content-Type: application/json`，但响应体长度为 0，请求约 100ms 完成。该证据属于远端单作品详情接口的软拦截，不是网络超时，也没有 401、403、429、验证码或 Cookie 过期证据。

列表快照下载能力上线后，新抓取到的收藏作品可以直接使用作者作品列表中的媒体元数据，不再请求单作品详情接口。但是，上线前已经进入 `biz_collect_run_item` 的活动下载项没有 `metadata_snapshot`，仍会回退到详情接口。

目前本地还有两个缺陷会放大这个兼容问题：

1. 详情接口的空响应软退避和真正的全局风控共用同一个冷却门，详情软退避会阻止作者列表抓取。
2. 作者列表再次发现某作品时，如果数据库中已有该作品的活动下载项，新运行只记录 `EXISTING_ACTIVE_DOWNLOAD`，不会把新快照回填给旧活动项。

结果是旧空快照项周期性触发详情软退避，作者列表抓取随即被延后，能够修复旧项的列表快照始终无法进入旧队列。

## 目标

- 明确区分全局强风控与单作品详情软退避。
- 详情软退避期间继续允许作者列表抓取、列表快照解析及基于已有媒体 URL 的下载。
- 不再让旧收藏队列反复调用已确认持续空响应的单作品详情接口。
- 使用有限轮、分页限量的作者列表刷新自动回填旧队列快照。
- 完整遍历后，为远端列表已不存在的旧项建立可解释的终态。
- 不删除本地作者、作品记录或已下载媒体。
- 保持 PostgreSQL 事务安全，并兼容现有 SQLite 测试初始化逻辑。

## 非目标

- 不改变单链接下载的详情接口行为；单链接没有作者列表上下文，仍允许使用详情接口。
- 不绕过明确的 Cookie、验证码、HTTP 401/403/429 或全局风控。
- 不增加新的外部依赖。
- 不提高作者列表每轮页数或取消已有的请求间隔、分页上限和队列去重。
- 不保存 Cookie、签名参数、完整请求 URL 或其他敏感上游字段。

## 冷却模型

`PlatformCookieService` 保留两个独立截止时间：

- **全局强风控**：明确的认证失败、验证码、HTTP 401/403/429 或限流证据。该状态阻止所有抖音抓取和下载 HTTP 请求，持续时间仍由前端配置的全局风控冷却控制。
- **详情接口软退避**：单作品详情接口重复返回 HTTP 200 空响应。固定短退避仅作用于详情接口，不阻止作者列表、快照解析和基于列表媒体 URL 的下载。

调用方必须显式选择所需的冷却判断，不再使用语义含混的统一判断：

- 作者列表抓取只检查全局强风控。
- 单作品详情请求同时检查全局强风控和详情接口软退避。
- 收藏下载使用有效列表快照时只检查全局强风控。
- Cookie 选择只因全局强风控而拒绝返回 Cookie；详情软退避由详情适配器单独判断。

F2 请求协调器仍保持单容器内公平串行，避免作者列表和单作品详情并发冲击远端。

日志必须包含明确作用域：`scope=GLOBAL_RISK` 或 `scope=DETAIL_API`，并保留 HTTP 状态、响应体长度、重试历史及错误分类。详情空响应不得再记录为 Cookie 失效。

## 旧队列恢复流程

### 1. 发现空快照项

收藏下载取得 `FETCH_DOWNLOAD_V1` 且 `metadata_snapshot` 为空的抖音项时，不调用单作品详情接口，而是：

1. 将该项恢复为 `RETRY_WAIT`，错误码写为 `LIST_SNAPSHOT_PENDING`。
2. 撤销本次 claim 增加的尝试次数，不消耗下载重试预算。
3. 将同一收藏任务内其他未运行的活动空快照项一并标记为等待列表快照，避免逐项触发相同流程。
4. 请求该收藏任务从游标 0 开始一个去重的快照刷新周期。
5. 给等待项设置合理的下一次可用时间，防止下载线程空转；快照回填成功时会提前唤醒。

刷新周期复用现有分页、每轮数量、页数保护、空页保护、请求间隔及活动任务去重。它跨有限轮推进，不在一次运行中无限制拉取作者全部作品。

如果收藏任务已停用或全局暂停，等待项保留，直到用户重新启用任务；不会自动越过用户的暂停设置。

### 2. 列表回填活动项

保存抓取计划时，对每个列表作品先查找相同 `platform_key + work_id` 的活动下载项：

- 列表项有合法白名单快照时，将快照写入所有匹配且快照为空的活动项。
- `QUEUED` 或 `RETRY_WAIT` 项恢复为可立即 claim，清除旧 F2/等待错误并重置因旧根因消耗的尝试次数。
- `RUNNING` 项只附加快照，不抢占锁、不修改锁令牌。当前处理若失败，失败事务发现数据库已经获得快照后，应重新排队且不消耗尝试次数。
- 当前抓取运行仍插入审计项，决策记录为已回填既有活动下载，不创建第二份实际下载。

快照写入、状态恢复和当前运行审计记录必须在同一数据库事务中完成。

### 3. 列表中不可下载或已不存在

- 如果列表明确返回该作品但标记为屏蔽、不可下载或媒体字段不足，匹配的等待项进入对应的 `SKIPPED_BLOCKED` 终态，并保留可读原因。
- 只有现有回填算法确认从游标 0 完成完整验证遍历后，仍处于 `LIST_SNAPSHOT_PENDING` 且没有快照的项，才进入 `SKIPPED_REMOTE_MISSING`，显示“远端列表已不存在”。
- 不使用单页未出现、顺序变化或临时空页作为远端删除依据。
- 终态只结束该历史下载项，不删除 `biz_collect_data`、`biz_collect_data_detail`、媒体库文件或作者元数据。
- 如果作品之后重新出现在作者列表，新的抓取仍可创建新的下载计划。

## 排队与优先级

下载 claim 优先选择已有合法快照的项，再处理等待快照或无快照项。这样旧兼容项不会阻塞已经可以直接下载的新作品。

同一作品的活动下载去重规则保持不变。列表回填是对既有活动项的补充，不改变“同一作品只实际下载一次”的约束。

刷新请求使用收藏任务现有的活动 job 去重键。如果该作者已有抓取 job，则复用现有 job；没有时才创建一个刷新 job。

## 并发与事务规则

- 不修改 `RUNNING` 项的 `process_state`、`locked_by` 或 `locked_at`。
- 所有状态更新必须带活动状态条件，避免复活已经完成或人工终止的项。
- 回填只在快照为空时执行，不能用较晚的不完整数据覆盖已有合法快照。
- 快照的 `aweme_id` 仍由下载适配器与 claim 的 `work_id` 二次校验。
- 成功下载或屏蔽终态继续清空快照，避免数据库长期膨胀。
- 任务停用、全局暂停和应用关闭时继续遵守现有可中断边界。

## 数据库影响

本设计复用现有字段：

- `biz_collect_run_item.metadata_snapshot`
- `process_state`
- `error_code` / `error_message`
- `attempt_count` / `available_at`
- 收藏任务现有 backfill 游标和验证状态字段

预计不需要新增列。SQL 使用 `JdbcTemplate` 参数化语句及当前事务边界，避免 PostgreSQL 专有的隐式类型行为；SQLite 测试模式继续覆盖相同状态机。

## 可观测性

新增或调整的关键日志：

- `DOUYIN_DETAIL_SOFT_BACKOFF`：详情接口软退避，包含 `scope=DETAIL_API`。
- `LIST_SNAPSHOT_PENDING`：旧下载项等待作者列表快照，不打印异常堆栈。
- `LIST_SNAPSHOT_REFRESH_QUEUED`：为某收藏任务创建或复用刷新 job。
- `LIST_SNAPSHOT_HYDRATED`：回填的任务、作品、活动项数量。
- `SKIPPED_REMOTE_MISSING`：完整遍历后确认远端列表不存在。
- 全局强风控继续记录 `scope=GLOBAL_RISK`。

远端软拦截的首次证据保留 ERROR/WARN 诊断；相同旧项等待快照属于预期状态，不重复输出错误堆栈。

## 测试与验收

### 冷却隔离

- 详情空响应只启动详情软退避。
- 详情软退避期间作者列表可以取得 Cookie 并执行。
- 详情软退避期间有效快照项可以解析和下载。
- HTTP 401/403/429、验证码或明确风险信号仍阻止所有抖音请求。
- 前端配置的全局冷却时长仍只控制强风控。

### 队列恢复

- 空快照收藏项不调用详情接口、不消耗尝试次数。
- 同任务多个空快照项只创建或复用一个刷新 job。
- 列表发现相同作品后回填原活动项并立即恢复下载。
- 已有快照不会被覆盖。
- `RUNNING` 项回填时不丢锁；当前失败后使用新快照重排。
- 快照项优先于空快照项 claim。
- 同作品不会产生重复实际下载。

### 终态与数据保留

- 局部页面未出现作品时不得判定远端删除。
- 完整验证遍历后，剩余等待项进入 `SKIPPED_REMOTE_MISSING`。
- 屏蔽作品进入 `SKIPPED_BLOCKED`。
- 本地作者、作品详情、历史记录和媒体文件保持不变。
- 后续重新出现的作品可以再次排队。

### 回归

- 运行相关 Java 定向测试。
- 运行 F2 Python 测试。
- 运行 Java 全量测试与 Maven compile。
- 运行 `git diff --check` 和敏感字段检查。

## 上线后预期

部署后，旧空快照队列首先进入等待状态，作者列表抓取不再被详情软退避阻断。随着现有分页回填在有限轮内推进，仍在远端作者列表中的作品自动获得快照并下载；完整遍历后未出现的历史项进入可解释终态。生产日志中不应再出现旧收藏项每五分钟续上全局冷却的循环。
